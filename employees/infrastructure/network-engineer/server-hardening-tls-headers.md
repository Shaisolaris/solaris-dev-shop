## 1. TLS posture scan (testssl)
- **Tool:** testssl.sh - a bash TLS/SSL tester that checks protocols, cipher suites, and crypto flaws on any host:port, plus a header pass. **License: GPLv2** - free to run and ship as a methodology dependency; flag to the host that any bundling/redistribution must honor GPLv2 (we invoke it, we do not vendor or copy its code).
- **Workflow (read-only, no host change):**
  1. Run testssl against the target host:443 (and any other TLS ports - mail, admin). Capture the full grade output to an artifact.
  2. Read the findings against a 2026 baseline: TLS 1.2 + 1.3 only (TLS 1.0/1.1 disabled), no weak/export/NULL ciphers, forward secrecy preferred, no known protocol flaws (ROBOT, BEAST-relevant ordering, etc.), valid + non-expiring-soon cert chain, OCSP stapling on, HSTS present.
  3. Produce a ranked remediation list. **Do not change the live TLS config outside a change window** - propose the smallest edge config change, confirm no client-lockout (old-client compatibility), then apply in-window and re-scan.
- HSTS ordering rule: confirm HTTPS works everywhere BEFORE enabling HSTS, and start with a short max-age, then ramp. preload only when the client understands it is hard to undo.

## 2. Edge security-header baseline
Set these at the web-server edge (NGINX/Apache/LiteSpeed/Caddy), NOT in the app, when edge control exists - it is faster, central, and survives app changes. Baseline set:
- `Strict-Transport-Security` (after section 1's ordering rule)
- `Content-Security-Policy` - deploy report-only first, collect violations, then enforce. CSP is the high-value, high-risk header; never enforce blind.
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy` - deny unused powerful features (camera, mic, geolocation, etc.)
- `X-Frame-Options: SAMEORIGIN` and/or CSP `frame-ancestors`
- Remove/obscure version-leaking banners (`Server`, `X-Powered-By`).
Validate with testssl's header pass or a dedicated header scanner; record the grade in the cleanup scorecard. (Caddy users: this composes cleanly with the existing Caddy/Uncloud ingress pattern in homelab-and-network-ops.md - set headers in the Caddyfile via the autogenerated-rules discipline, never hand-edit the generated file.)

## 3. CIS-benchmark host hardening
The CIS Benchmarks are vendor-published, consensus configuration baselines per platform (Linux distros, web servers, cloud, DB). Use them as the checklist, not as dogma.
- **Levels:** Level 1 = essential, minimal operational impact ("must do" basic hardening). Level 2 = defense-in-depth, may impact functionality (apply where the workload tolerates it). Start at Level 1; escalate selectively.
- **Scope for a hosting cleanup:** OS baseline (SSH hardening - key-only auth, no root login, modern KEX/ciphers; firewall default-deny inbound; auto security updates; minimal services), web-server baseline (TLS as section 1, headers as section 2, request-size + method limits, directory listing off, sensitive-file access denied), and account/log hygiene (no shared accounts, audit logging on).
- **Method:** assess first (read-only) against the relevant CIS benchmark, score Level-1 pass/fail, then remediate smallest-change-first in a change window with rollback noted in platform vocabulary. Re-assess after. Open-source assessment tooling (CIS-CAT-style scripts, OpenSCAP, Lynis) can produce the initial score; treat their output as input to judgment, not a verdict.
- License note: CIS Benchmarks PDFs are free for non-commercial internal use under CIS terms; the automated CIS-CAT Pro assessor is membership-gated. OpenSCAP/Lynis are open-source (LGPL/GPL) alternatives for the scan. Flag the CIS-CAT gating to the host if they want the official assessor.

## 4. Execution path (wired vs plan-only)
- WIRED when host grants SSH/edge access: run testssl + header scan + a hardening assessor read-only; propose ranked changes; apply smallest-first in a change window; re-scan to confirm.
- DELEGATED: WordPress-application-layer cleanup (plugin/transient/autoload/caching) -> wordpress-master. CI/secret/container supply-chain gates -> devops-engineer.
- PLAN-ONLY otherwise: deliver the scan plan + baseline checklist + remediation template; never claim a host change not made.
- Doctrine carried in: read-only-first, change-window-only for live changes, lockout-prevention (keep an out-of-band path before touching SSH/firewall), rollback in platform vocabulary, SHA-pin any CI step that invokes these tools.
