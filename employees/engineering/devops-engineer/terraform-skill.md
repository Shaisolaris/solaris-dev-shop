## Decision rules

### When to use Terraform vs alternatives
- **Terraform / OpenTofu** = default for any multi-cloud or AWS/GCP/Azure infrastructure
- **Pulumi** = when client team strongly prefers TypeScript/Python expressiveness
- **AWS CDK** = AWS-only, when team already deep in AWS native and wants TypeScript
- **CloudFormation** = legacy AWS, only when client is already on it
- **Kustomize / Helm** = Kubernetes manifests, NOT infrastructure (different tool, different layer)

### OpenTofu vs Terraform
- **Default to OpenTofu** for new client projects post-2024 - fully Terraform-compatible, MPL-2.0 licensed (no BSL surprise)
- **Stay on Terraform** if client already has it in production AND no compelling migration reason
- Both share `.tf` syntax; module ecosystem fully shared

### Module structure decisions
- **Composition over inheritance** - small focused modules combined, not deep inheritance trees
- **Registry-backed modules first** (terraform-aws-modules family for AWS) - battle-tested, version-pinned, well-documented
- **Roll your own only when** registry doesn't fit OR you need bespoke abstraction
- **Module versioning** - semantic versioning, pin to exact version in production (`= 1.2.3`), allow minor in dev (`~> 1.2`)

## Standard module structure (Solaris template)

```
my-module/
├── main.tf          # primary resources
├── variables.tf     # input variables with types + descriptions + validation
├── outputs.tf       # output values for parent modules to consume
├── versions.tf      # required Terraform + provider versions
├── README.md        # generated by terraform-docs (auto-update via pre-commit)
├── examples/
│   ├── basic/       # minimal usage example (testable)
│   └── complete/    # full-feature usage (testable)
└── tests/
    └── basic.tftest.hcl  # native Terraform test
```

**Why this structure:**
- `versions.tf` separate from `main.tf` so version pins are obvious in PR diffs
- `examples/` are testable as integration tests (not just docs)
- `tests/` uses Terraform's native test framework (1.6+) - no Terratest unless deep Go testing needed
- README.md auto-generated from variable + output blocks via terraform-docs

## Production patterns

### State management
- **Remote state** mandatory for any team-shared or production infra
- **Backends**: S3 + DynamoDB lock (AWS), GCS (GCP), Azure Storage (Azure), Terraform Cloud / HCP Terraform (managed)
- **State per environment** - never one giant state file across dev/staging/prod
- **State per service** - break by domain when state grows large
- **Encrypt state at rest** - backend-side encryption mandatory
- **Lock state** - DynamoDB lock for S3 backend; otherwise concurrent runs corrupt state
- **No secrets in state** - `sensitive = true` flag + Vault/SSM for secrets, never plaintext in `.tfvars`

### Workspaces vs separate state files
- **Workspaces** for multi-tenant single-config (rarely the right choice)
- **Separate root modules per environment** is usually cleaner - `envs/dev/` `envs/staging/` `envs/prod/` each with its own state
- Hybrid: shared modules + per-env root modules + per-env state files

### Drift detection
- **`terraform plan` on schedule** (daily) against production - alert on drift
- **Cloud-native drift detection** - AWS Config, GCP Asset Inventory, Azure Resource Graph
- **Don't auto-remediate** - drift may be intentional emergency change; route to human review

### Policy as code
- **OPA / Sentinel** - for orgs with compliance requirements (SOC 2, PCI, HIPAA)
- **`tfsec` / `Checkov` / `Terrascan`** - pre-commit + CI security scanning
- **Conftest** - generic policy testing
- **Don't gate everything** - prioritize blocking on PII exposure, public-by-default storage, missing encryption

## CI/CD for Terraform (GitHub Actions reference)

```yaml
name: terraform-ci
on:
  pull_request:
    paths: ['**.tf', '**.tfvars']

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.9.x
      - run: terraform fmt -check -recursive
      - run: terraform init -backend=false
      - run: terraform validate

  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aquasecurity/tfsec-action@v1
      - uses: bridgecrewio/checkov-action@master

  plan:
    needs: [validate, security]
    runs-on: ubuntu-latest
    permissions:
      id-token: write       # OIDC
      contents: read
      pull-requests: write  # PR comment
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.TF_PLAN_ROLE_ARN }}
          aws-region: us-east-1
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform plan -out=tfplan -no-color
      - uses: actions/upload-artifact@v4
        with:
          name: tfplan
          path: tfplan
      # PR comment with plan summary via terraform show -json + jq
```

### Critical CI patterns
- **OIDC for cloud auth** - never long-lived AWS access keys in GitHub Secrets
- **Plan on PR, apply on merge to main** - never auto-apply on PR
- **PR comment with plan summary** - humans review the diff
- **Required approvals** for production environment
- **Lock production environment** with manual approval gate

## Testing patterns

### Native Terraform test (1.6+)
```hcl
# tests/basic.tftest.hcl
run "basic" {
  command = plan

  variables {
    name = "test-vpc"
    cidr = "10.0.0.0/16"
  }

  assert {
    condition     = aws_vpc.this.cidr_block == "10.0.0.0/16"
    error_message = "VPC CIDR mismatch"
  }
}
```

### Terratest (Go) - when native test isn't enough
- Real provisioning + assertion + cleanup
- Slower but catches integration issues native test can't
- Use when module spans multiple providers OR has complex post-provision wiring

### Decision rule
- **Default to native Terraform test** for unit-level module assertions
- **Add Terratest** only when integration testing is genuinely required

## OpenTofu compatibility

- **Syntax**: 100% compatible with Terraform 1.5+; nothing to change
- **State**: OpenTofu can read Terraform state and vice versa (within compatible versions)
- **Provider compatibility**: full Terraform Registry support
- **Module compatibility**: full Terraform Registry support
- **CI tooling**: replace `setup-terraform` action with `setup-opentofu` (or use both for migration window)
- **Migration path**: pin OpenTofu version, run both in CI for 1-2 weeks, then drop Terraform

## Secrets in Terraform - discipline rules

- **Never commit `.tfvars`** with secrets - `.gitignore` always
- **Use cloud secret manager** - AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, HashiCorp Vault
- **`sensitive = true`** on every variable that holds a secret - prevents log leakage
- **`data` sources for secrets** - read at apply time, never in source code
- **Encrypt remote state** - secrets land in state if not careful; backend encryption is the safety net
- **Rotate regularly** - secrets that have ever been in state should be rotated when state is decommissioned

## Anti-patterns (do NOT do)

- ❌ Hardcoded credentials anywhere
- ❌ `terraform apply --auto-approve` in CI without human gate for production
- ❌ One giant state file across all environments
- ❌ Workspaces for environment separation (use separate root modules instead)
- ❌ Manual changes in cloud console after Terraform manages the resource (drift accumulates)
- ❌ Module > 500 lines without decomposition
- ❌ Provider version unpinned in production (`>= 4.0` is a foot-gun)
- ❌ Skipping `terraform plan` review before apply
- ❌ Storing `.tfstate` in git (it has secrets and conflicts horribly)
- ❌ Using `local-exec` provisioner for anything important (fragile, non-idempotent)

## When to bring in the Terraform MCP server (optional)

For sessions that need live registry lookups (latest module versions, provider arg discovery):
```bash
# Optional: Terraform MCP for live registry queries
agent mcp add terraform -- npx -y @hashicorp/terraform-mcp-server
```
Don't install preemptively - only when registry-freshness matters in the current session.

**CONNECT - hashicorp/terraform-mcp-server (MPL-2.0, official HashiCorp).**
- **What it does:** queries the live Terraform Registry - search modules/providers, pull current versions, and discover provider/resource arguments and their docs straight into context.
- **When to call it:** before writing a provider block or module call where the arg surface may have changed since training cutoff, or to pin to the actual latest module version instead of a guessed one. This is the anti-hallucination backstop for Terraform authoring - pair it with antonbabenko's authoring playbook above (the playbook is *how* to structure; the MCP is *what's current*).
- **When NOT to:** stable args you're certain of; offline/air-gapped runs.
- Host installs `@hashicorp/terraform-mcp-server` (npx); no secret needed for public registry reads.
